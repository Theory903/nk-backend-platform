# Design: NK Backend Platform — Contract-First Platform Program

Generated by office-hours on 2026-08-30
Status: DRAFT
Mode: Startup

## Problem Statement

NK has outgrown the cookiecutter-demo category but has not yet earned the
“Next.js for FastAPI” promise. The repository contains many useful protocols,
adapters, tests, and generated modules. A new team still has to hand-wire
routers, choose implementations, build identity HTTP, make state durable,
operate jobs and agents, and assemble production deployment.

The first product proof is simple: a platform engineer runs `nk init`, creates
one business module, and gets a reachable, documented, testable API without
editing NK framework files. The full product then expands that same generated
app into a durable, tenant-safe, observable, agent-capable, deployable system
with tested industry packs.

## Demand Evidence

- Current evidence is early and not yet independently verifiable: unnamed
  design partners represent platform teams and agencies.
- The reported status quo is agency-specific backend assembly costing roughly
  one to four engineer-weeks per client backend.
- The observed failure is concrete: builders bypassed the current template
  instead of completing the generated workflow.
- This is enough to validate a delivery problem, not enough to assume that every
  C1–C20 capability is already a demanded product.

## Status Quo

Teams assemble each backend from internal templates, copied FastAPI modules,
provider SDKs, infrastructure manifests, and agency-specific deployment code.
The repeated cost is not only initial scaffolding. It is divergence: auth,
tenant filtering, jobs, audit, AI providers, readiness, CI, and deployment are
reimplemented with different failure semantics in every service.

## Target User & Narrowest Wedge

The first buyer is a platform engineer or backend lead accountable for
shipping more services with fewer engineer-days. The first wedge is:

```text
nk init → nk generate module crm.leads → nk dev
       → auto-mounted /api/v1/crm/leads
       → OpenAPI + tests + provider-safe DI
```

The agency/consultancy segment is a second acquisition path because it has a
clear repeated-backend problem, but it should not force the first architecture
to optimize for white-labeling before the framework loop works.

## Premises

1. The first product proof is a generated module that runs and auto-mounts
   without hand-editing framework code.
2. The full NK vision is a modular monolith framework with durable runtime,
   identity/tenancy, AI/agent protocols, ops, config-driven deployment, and
   industry packs, not one giant first release.
3. Complete product packs are the long-term differentiation; the framework loop
   earns the right to build them.
4. Partner evidence is currently unnamed, so every major wave needs a concrete
   validation checkpoint before it becomes a paid-product commitment.

## What Makes This Cool

The “whoa” moment is not a generated directory. It is seeing a domain module
become a real API by following a convention, then watching the same project
move from local Compose to a guarded staging deployment without rewriting its
business code. AI code generation can write files; NK can own the contracts,
runtime guarantees, production topology, and complete product packs that make
those files safe to operate.

## Approaches Considered

### Approach A — Wedge-first product plan

Build only `nk init` → module generation → auto-mounting, with minimum runtime
support. This is fastest to validate and has the smallest first release, but
it leaves the complete platform architecture under-specified.

### Approach B — North-star blueprint / big-bang specification

Specify and implement every capability horizontally before releasing. This
maximizes up-front coverage but creates long feedback loops, high integration
risk, and a strong chance of polishing abstractions no design partner needs.

### Approach C — Contract-first, vertically staged platform program

Define the complete target contracts, ownership, sync semantics, scale stages,
packs, and production gates first. Deliver vertical slices in dependency order,
and require each slice to pass a generated-app acceptance test plus a partner
validation checkpoint. This keeps the full vision while making each release
useful and falsifiable.

## Recommended Approach

Use Approach C. Treat the program as one product architecture with staged
release trains, not as unrelated feature projects. Every capability must have:

```text
contract → implementation adapter → config surface → health/ready check
→ metrics/tracing → problem errors → contract tests → migration/runbook
```

The framework owns conventions, policies, harnesses, and release gates.
Postgres, Redis, queues, IdPs, LLMs, vector stores, workflow engines, cloud
load balancers, and Kubernetes remain replaceable infrastructure adapters.

## Product Architecture

### Ownership layers

| Layer | Owns | Must not own |
|---|---|---|
| Generator / `nk` | init, profiles, scaffolds, checks, lifecycle verbs | Business rules |
| Core kernel | config, DI, errors, IDs, request context, policy hooks | Vendor SDKs |
| Web/API | discovery, versioning, middleware, protocol surfaces | Persistence details |
| Identity | authn, authz, orgs, sessions, keys, SCIM | Product-specific roles |
| Data | Repository, UoW, tenancy scope, migrations | HTTP handlers |
| Async / workflows | jobs, outbox, retries, DLQ, durable execution | UI concerns |
| AI / agents | gateway, retrieval, tools, guardrails, runs, memory | Direct vendor imports |
| Platform | files, audit, idempotency, notifications, billing hooks | Industry invariants |
| Ops / deploy | build info, metrics, SLOs, Helm, GitOps, supply chain | Domain workflows |
| Packs | complete vertical workflows and defaults | Forked framework core |

### Non-negotiable invariants

1. A module router is discovered by convention and mounted exactly once under
   `/api/v1/{domain}`.
2. `platform.yaml` is the runtime configuration source for providers, modules,
   scale stage, observability, and deployment intent. Environment variables
   provide secrets and deployment-specific overrides only.
3. Business code imports NK protocols, never provider SDKs directly.
4. Postgres is the source of truth for durable state; Redis is cache,
   coordination, rate-limit, and session infrastructure where configured.
5. Every tenant-scoped request, job, tool call, event, and workflow carries
   trusted organization context.
6. Unsafe mutations have idempotency and audit behavior according to profile.
7. Long-running work is resumable, observable, bounded, and replayable.
8. Production deployment is a separate migration Job plus API, stream, and
   worker workloads when the selected stage requires them.
9. Minimal stays light. Optional profiles add dependencies without leaking AI,
   fintech, or broker imports into minimal applications.
10. Every promise has a generated-app test and an operator runbook.

## Sync Contracts

“Sync” is a product concept, not an implementation detail. Each sync has one
source of truth, delivery semantics, retry policy, observability, and replay
path.

| Sync | Source of truth | Mechanism | Failure / recovery |
|---|---|---|---|
| Config sync | `platform.yaml` + env secret refs | schema validation + resolved spec | doctor reports drift; explicit patch rollback |
| Generator sync | template version + generated manifest | `nk init` pins framework version | upgrade command, diff, migration notes |
| DB sync | Postgres schema and migrations | Alembic expand/contract | PreSync Job; backup/PITR and rollback runbook |
| Event sync | committed outbox rows | relay → broker → consumers | retry, DLQ, replay, idempotent consumers |
| Identity sync | IdP / SCIM directory | signed/authenticated provisioning | cursor checkpoints, quarantine, audit |
| Tenant sync | org directory and membership store | durable registry + cache invalidation | deny closed; rebuild cache from Postgres |
| Job sync | queue plus durable job/DLQ records | worker ack/retry/replay | no silent drop; `nk jobs replay` |
| Workflow sync | durable journal/checkpoint store | local → Temporal/DBOS adapter | resume after crash; explicit side-effect policy |
| Knowledge sync | source document version | ingest pipeline + indexed event | content hash, partial retry, stale-index status |
| Deployment sync | Git commit + Helm values | Argo/Flux desired state | health gate, canary rollback, drift alert |
| Telemetry sync | app spans/metrics/logs | OTLP collector | bounded queues, sampling, dropped-signal metric |
| Pack sync | pack manifest + framework version | profile expansion and compatibility checks | migration contract; no hidden fork |

## Production Lifecycle

### Environments

1. **Dev:** `nk dev`, Compose dependencies, fake/local providers only where
   explicitly marked, fast reload.
2. **CI:** generator profile matrix, static import guards, contract tests,
   real Postgres/Redis legs, image build, SBOM, vulnerability scan.
3. **Staging:** Helm install/upgrade, migrations as PreSync, smoke tests,
   readiness and telemetry validation, chaos drills for jobs/outbox.
4. **Production:** canary or blue/green, SLO burn gate, signed image,
   ExternalSecrets, default-deny NetworkPolicy, rollback command.
5. **DR:** restore drills, documented RPO/RTO, cell or region failover only
   after the relevant scale stage is earned.

### Scale stages

| Stage | Product shape | Exit evidence |
|---|---|---|
| S0 | Laptop / Compose | Generated minimal app works locally |
| S1 | Single cluster, API + worker | Two API replicas, backup, basic HPA/PDB |
| S2 | HA monolith + stream split | Multi-AZ, PreSync migrations, SLO under load |
| S3 | Workload-split same image | Independent API/stream/worker scaling and queue lag |
| S4 | Data and async scale-out | Read replicas, Kafka/Qdrant/Temporal where measured |
| S5 | Cells and multi-region | Org-to-cell routing, residency, restore/failover drill |
| S6 | Edge and hyperscale | Ingest edge, global bus/materializers, chaos game-day |

No stage is activated by marketing language alone. `scale.stage` must map to
validated Helm values, required dependencies, exit checks, and an operator
runbook.

## Release Waves

### Wave 0 — Framework loop and validation

- Add module discovery with deterministic import order, duplicate detection,
  prefix/tag conventions, and a safe import error report.
- Make generated CRUD use a runnable default repository/service factory.
- Add `nk init` alias at the generator boundary and generate a lockfile.
- Add generated-app tests proving route reachability, OpenAPI inclusion,
  duplicate prevention, and a malformed module failure message.
- Validate with at least two unnamed design partners using a hands-off script.

**Exit:** a new user can generate, add a module, run it, and see its endpoint
without touching framework router code.

### Wave 1 — Config and boot kernel

- Version `platform.yaml`; define providers, modules, scale, deployment,
  observability, and framework version.
- Implement resolved configuration and doctor checks for profile/config drift.
- Register CORS, build info, readiness checks, middleware, and tenant boot.
- Define app lifecycle ownership so config is read once and resources are
  shared rather than independently constructed by every module.

**Exit:** generated `saas` and `agentic` apps have truthful readiness and
consistent production defaults.

### Wave 2 — Identity and tenancy product

- Replace the default auth surface with identity-owned route groups for login,
  refresh, logout, password lifecycle, MFA, OAuth, sessions, and API keys.
- Wire SCIM service through DI and define provisioning idempotency.
- Implement membership registry and tenant modes: shared-schema first, then
  schema-per-tenant and DB-per-tenant behind explicit profiles.
- Add authn/authz/tenant integration tests against real Postgres where needed.

**Exit:** protected routes, org context, session/key revocation, and
cross-tenant isolation work in a fresh generated `saas` app.

### Wave 3 — Durability, async, and ops

- Implement durable session, audit, idempotency, membership, webhook replay,
  job/DLQ, and agent checkpoint stores.
- Add worker CLI, job status, replay, outbox relay, AsyncAPI generation, and
  poison-message handling.
- Add owned metrics, `/build-info`, authenticated ops controls, OTel collector
  config, PrometheusRules, and incident/DLQ/PITR runbooks.

**Exit:** kill-worker, restart, replay, and audit exercises preserve intent and
leave an observable trail.

### Wave 4 — Deploy-from-config

- Generate Helm chart with API, stream, worker, migration Job, services,
  ingress path split, HPA, PDB, topology spread, NetworkPolicy, PSS, and
  ExternalSecrets hooks.
- Add stage values S1–S3, Argo/Flux application examples, CI image push,
  SBOM, Trivy CRITICAL gate, and Cosign signing.
- Implement `nk start`, `nk migrate`, `nk seed`, and `nk deploy`.

**Exit:** staging can be installed from `platform.yaml`, migrated safely,
smoke-tested, canaried, and rolled back.

### Wave 5 — Agent and protocol surfaces

- Add `/runs`, `/threads`, `/store`, stream endpoints, run lifecycle, budgets,
  guardrails, tenant policy, and durable checkpoints.
- Add MCP Streamable HTTP server with tool registry, auth, quotas, audit, and
  cancellation. Keep the existing client bridge separate.
- Add `nk eval`, usage/cost aggregation, and agent contract/eval suites.

**Exit:** an agentic app can resume a run after restart and expose a policy-safe
  stream without starving CRUD traffic.

### Wave 6 — Knowledge and multimodal

- Add source loaders for PDF, DOCX, and URL with SSRF/content limits.
- Build parse → chunk → embed → dense+sparse index → RRF → rerank → cite.
- Add image/vision/STT/TTS protocols and provider adapters with cost/timeout
  accounting.
- Implement sandbox backends with network-deny defaults and explicit mounts.

**Exit:** ingestion is replayable and observable; retrieval has measurable
  quality/latency evals; untrusted tool execution is isolated.

### Wave 7 — Platform commerce and delivery

- Notifications: provider interface, email/in-app channels, preferences,
  templates, delivery attempts, retry/DLQ, and tenant policy.
- Billing: Stripe adapter, product/price/subscription models, entitlements,
  signed webhook handling, reconciliation, and test clocks/fakes.
- Webhooks: endpoint registration, encrypted secrets, delivery attempts,
  retry schedule, DLQ, replay, and idempotent receiver behavior.

**Exit:** a SaaS pack can sell access, notify users, and deliver/replay events
without business teams rebuilding these surfaces.

### Wave 8 — Industry packs and white-label

- **Fintech:** ledger, limits, maker-checker, KYC/AML vendor seam,
  reconciliation, reports, strict audit/idempotency.
- **CRM:** accounts, contacts, leads, opportunities, activities, ownership,
  pipeline stages, import/export, and notifications.
- **ERP:** organizations, catalog, inventory, purchasing, orders, invoices,
  approvals, and accounting integration seams.
- **Commerce:** products, prices, carts, checkout, orders, fulfillment,
  refunds, tax/shipping seams, and payment webhooks.
- **Data platform:** sources, connectors, ingestion jobs, datasets, lineage,
  permissions, quality checks, and catalog APIs.
- **White-label:** branding/domain slots, pack manifest, entitlement rules,
  tenant configuration, and upgrade/migration contracts.

Every pack ships fixtures, seed data, permissions, events, OpenAPI/AsyncAPI,
contract tests, upgrade notes, and a generated demo journey. Packs cannot
modify framework core or import vendors directly.

### Wave 9 — Extraction and maintenance

- Extract only stabilized contracts and adapters into `nk-core`.
- Keep the generator as a compatibility-tested distribution surface while
  versioning generated framework/runtime dependencies.
- Add SemVer compatibility checks, changelog generation, deprecation windows,
  upgrade diffs, and a framework conformance suite.

**Exit:** a generated app can upgrade framework versions with a reported
migration plan and no silent template drift.

## Testing and Evaluation Program

Every wave must run:

- generator matrix: `minimal`, `saas`, `ai-saas`, `agentic`, `fintech`;
- lint, type, import-leak, lockfile, and generated-project checks;
- contract tests for every provider adapter;
- real Postgres/Redis legs for durability and tenancy;
- restart, retry, timeout, duplicate, replay, and partial-failure tests;
- OpenAPI and AsyncAPI snapshot/compatibility checks;
- security tests for auth boundaries, tenant isolation, SSRF, tool inputs,
  secrets, signed webhooks, and image supply chain;
- load tests matched to the selected scale stage;
- agent evals for tool selection, guardrails, retrieval quality, latency, and
  cost where the profile includes AI.

The first customer-facing metric is time-to-working-module, with a target of
under 15 minutes for a new platform engineer after dependencies are installed.
The first product validation is two hands-off partner sessions where the user
completes the wedge without framework intervention.

## Dependencies

- Freeze the generated app contract before extracting `nk-core`.
- Complete Wave 0 before building pack-specific router conventions.
- Complete config and tenant context before durable stores and HTTP surfaces.
- Complete durability and ops before promising deploy-from-config.
- Complete agent run identity/checkpoints before MCP, workflow, or sandbox
  production claims.
- Secure provider contracts and secrets handling before billing, IdP, or
  external ingestion adapters.

## The Assignment

Schedule two hands-off trials with one platform engineering team and one agency
technical lead. Give each the same script: install, run `nk init`, generate a
module, add one field, run checks, and call the endpoint. Record every point
where they leave the paved road. Do not build the next broad capability until
the first trial shows whether auto-mounted modules solve the bypass behavior.

## What I Noticed

You consistently pushed toward the whole platform rather than a single feature:
“all features, all syncs, all productions, all packs.” That is the right
north-star requirement for the design, but your own answers also identified the
product risk: the partners are unnamed, the current assembly cost is only a
range, and users bypassed the template. The contract-first staged program keeps
the complete target visible while forcing each lake to prove value before the
next one is funded.
