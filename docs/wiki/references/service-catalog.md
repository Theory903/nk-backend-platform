This page maps the template's optional services to the profile that enables
them. A capability marked optional is not automatically a running production
dependency. Confirm the generated `platform.yaml`, imports, and health checks
for the project you generated.

## Product use cases

The product-first CLI accepts these intent labels and resolves them to the
current architecture profiles:

```text
minimal-api → minimal
saas, enterprise-saas, crud-platform, integration-api → saas
data-platform, search-platform, automation-platform, event-platform → saas
knowledge-platform, ai-saas, ai-knowledge → ai-saas
agentic → agentic
fintech → fintech
internal-tool, developer-api, webhook-platform, high-scale-api → saas
custom → interactive composition
```

These labels make product intent explicit, but they do not imply that a
dedicated CRM, ERP, search, data, or high-scale domain pack is generated.
Business behavior is added through generated modules and application code.

## Application and API

| Capability | Profiles | Entry points |
| --- | --- | --- |
| FastAPI application | All | `web/application.py` |
| REST routers | All | `web/api/router.py` |
| Business modules | Database profiles | `core/module_discovery.py`, `nk generate` |
| API Studio | Generated app | `/api/docs`, `web/api/docs/views.py` |
| Swagger and ReDoc | Generated app | `/api/swagger`, `/api/redoc` |
| OpenAPI document | Generated app | `/api/openapi.json` |
| Health/readiness | All | `/api/health`, `/api/ready` |
| Metrics | When Prometheus is enabled | `/api/metrics` |

The API router applies authentication and CSRF dependencies to protected
routes when users are enabled. Health and readiness are intentionally public
for orchestrator probes.

## Identity and tenancy

The `saas`, `ai-saas`, `agentic`, and `fintech` profiles enable the local
identity baseline. It includes registration, login, password reset and
verification routes, users, JWT and optional cookie auth, sessions, API keys,
MFA/TOTP primitives, provider adapters, permissions, and tenant context.

Key modules:

- `identity/http.py` and `identity/platform_http.py` — public identity routes;
- `identity/session.py` and `identity/api_keys.py` — session and key contracts;
- `identity/deps.py` and `identity/permissions.py` — request authorization;
- `platform/tenancy.py` and `identity/tenant_context.py` — tenant resolution;
- `data/rls.py` — database defense-in-depth helpers.

OIDC, SAML, LDAP, mTLS, cloud IAM, and edge WAF configuration remain
deployment integrations. They are not implied by enabling local identity.

## AI, knowledge, and agents

| Capability | Profile | Main entry points |
| --- | --- | --- |
| Model gateway/provider routing | `ai-saas`+ | `ai/gateway/`, `ai/providers/` |
| Vector storage and embeddings | `ai-saas`+ | `ai/embeddings.py`, `ai/knowledge/` |
| Ingestion and chunking | `ai-saas`+ | `ai/knowledge/ingestion.py` |
| Authorization-first RAG | `ai-saas`+ | `web/api/knowledge.py`, `ai/knowledge/answer.py` |
| Graph retrieval | `agentic` | `ai/knowledge/graph.py` |
| Bounded agent runtime | `agentic` | `agents/runtime.py`, `agents/loop.py` |
| MCP bridge/protocol routes | `agentic` | `agents/mcp_bridge.py`, `web/api/agent_protocol.py` |
| Evaluation and governance | AI profiles | `scripts/eval.py`, `agents/evaluation/` |

The AI stack is adapter-based. Provider credentials, model selection,
production vector infrastructure, tool policy, and evaluation gates must be
configured for the generated application.

## Data and infrastructure

| Capability | Profiles/options | Main entry points |
| --- | --- | --- |
| SQLAlchemy/PostgreSQL | `saas`+ baseline | `db_sa/`, `data/adapters/sqlalchemy/` |
| Mongo/Beanie and other ORMs | Explicit options | `db_beanie/`, `db_tortoise/`, `db_ormar/`, `db_piccolo/` |
| Redis state and locks | `saas`+ baseline | `core/state.py`, `stores/`, `core/locks.py` |
| RabbitMQ, Kafka, NATS | Explicit options | `services/`, `web/api/` |
| Task queue and DLQ | `saas`+ baseline | `jobs/__init__.py`, `tkq.py` |
| Files/object storage | Identity-enabled projects | `platform/files/` |
| Audit/idempotency/ledger | `fintech` | `platform/audit/`, `core/idempotency.py`, `industry/fintech/` |
| Webhook signing/delivery | Optional integration | `integrations/webhooks/` |
| Notifications and billing | Optional platform services | `platform/notifications.py`, `platform/billing.py` |

Repositories and unit-of-work protocols are intended to keep application code
independent of a specific data vendor. Replace development adapters with
durable implementations before relying on them across processes or restarts.

## Deployment and observability

The generated project can include Docker Compose, a production Compose
overlay, Helm charts, OpenTelemetry Collector, Prometheus, Loki, Tempo,
Grafana, CI, migration jobs, worker workloads, and autoscaling. The exact set
is determined by the selected options and is recorded in `platform.yaml`.

Read [deployment](../04-deployment.md) for security and durability requirements.

## Evidence and boundaries

The catalog is verified against generated application composition in
`web/application.py`, profile definitions in `fastapi_template/profiles.py`,
and contract tests under `fastapi_template/template/{{cookiecutter.project_name}}/tests/`.
Some modules are contracts or development defaults rather than complete
managed services. Their production status must be stated explicitly in any
application-specific documentation.
